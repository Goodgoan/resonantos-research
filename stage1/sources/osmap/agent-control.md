## Summary

- "Agent Control" is a single-agent browser-automation loop that lives in the **extension side panel**, not in the service worker and not on the host. The side panel asks the local bridge host for one next action at a time (`POST /augmentor/next-action`), the host forwards that to an OpenAI-compatible `/chat/completions` endpoint, sanitizes the JSON reply with a keyword blocklist, and returns it; the side panel then executes the step by `chrome.tabs.sendMessage` to the injected content script, which performs DOM clicks/typing. [inspected, high]
- The **real enforcement of blocked actions is in the content script** (`ext/content.js`), not in the runner, UI or host. The runner executes first and reacts to an `approvalRequired/humanHandoff` refusal in the result. The `userApproved` flag that the runner sends on re-execution is accepted by content.js but never read, so no in-panel approval can bypass the content-script gate. [inspected, high]
- Host-side and extension-side "sanitizers" are regex keyword blocklists on step text/URL (`seed|password|wallet|sign|buy|...`). They catch obvious phrases, not intent; a planner that says "Tweet", "Purchase", "Place order", "Continue" passes them. The content-script DOM heuristics (type=submit, button-in-form, commit verbs, field classifier) are the deeper layer. [inspected, high]
- The LLM planner is never exercised in any CI lane: unit tests stub `fetch`; the live Chrome lane boots the bridge with no provider key and scripts every decision via a `globalThis.__resonantosNextActionOverride` hook that ships in production code. [inspected, high]
- `agent-control-certification/run-certification.mjs` (#223 "certification gate") is not wired into any workflow or npm script; it is a manual script. The default lane `npm run test:browser-first` picks up only `browser-first/test/*.test.mjs` (top-level, non-recursive). [inspected, high]
- Durable jobs persist to `chrome.storage.local` (keys `augmentorBrowserJobs`, `augmentorActiveBrowserJob`); after a side-panel reload, `running`/`approval` jobs are flipped to `paused`; resume re-queues through the scheduler, which restarts the loop with an **empty planner history** even though step records are kept for display. [inspected high; history-loss inference medium]
- The live lane's public-submit scenario (#240) uses `public_submit_contract=auto` by default; in that mode a regression of the handoff yields status `gated` and overall `passed-with-gates`, not a failure. Only manual dispatch with `required` fails. [inspected, high]
- No A2A / Agent Card / agent-to-agent mechanism exists in the repo (grep over js/mjs/ts/md/json/yml: zero hits). "Delegation" in this codebase is add-on/harness delegation to local runtimes (Hermes/OpenCode), not agents messaging agents. [inspected, high]

## Planning

**Where the plan is produced.** [inspected, high] Two host routes exist (`host/agent-control-host-service.mjs:437-457`):
1. `POST /augmentor/control-plan` -> `executeControlPlan` returns a bounded batch plan `{summary, steps[<=8], needsApproval, approvalReason}` (sanitized at 179-206).
2. `POST /augmentor/next-action` -> `executeNextAction` returns one decision `{thought, status: continue|done|needs_approval|blocked, action|null, approvalReason, doneSummary, strategyPhase, strategyRationale, completionCheck}` (sanitized at 119-177).

The host builds a system prompt (lines 272-294 / 349-375) that enumerates allowed step types and tells the model "Never plan wallet signing, seed phrases, passwords, payments, public posting, account login, destructive document changes, or public form submission." The user message is `JSON.stringify({goal, pageSnapshot, history, strategyRunbook})` (295-299 / 376-381). The call is a plain `fetch` to `${route.apiBaseUrl}/chat/completions` with `Authorization: Bearer <apiKey>` (300-314); `response_format: json_object` and `reasoning_effort` only when `providerType === "openai"` (312). Provider routing and secret reading are injected dependencies (`providerRouteForModel`, `readProviderSecrets`, 218-257); a missing key throws `"<label> credential missing. Falling back to deterministic browser control is required."` (263-265).

**Snapshot the model sees.** `trimPlannerSnapshot` (1-16) caps title 180, url 800, text 6000 chars, 30 links, 40 controls, 30 fields, 30 tabs, plus `walletProviders`. The content script produces up to 80 controls and 80 fields (`content.js:236-250`), each control carrying `ref`, visible text, tag, role, aria-label and `approvalRequired: isSubmitLikeElement(element)` (244).

**Which route is live.** [inspected, high] The runner uses only the next-action loop: `runControlCommand` sets `planner: "observe-act-verify-loop"` (`agent-control-runner.js:888-893`) and `continueControlLoop` calls `requestNextControlAction` each iteration (471). `planAgentControlSteps`/`requestControlPlan` (`control-planning-service.js:35-57, 115-130`) have **no callers** in `side-panel.js` or `ext/lib/*` (grep) - the `/augmentor/control-plan` route is reachable over the bridge but unused by the shipped extension. [hypothesis: legacy, medium]

**Extension-side runbook.** `buildControlRunbook` (`agent-control-planner.js:234-268`) classifies the goal by regex into a task class (56-64) and attaches scenario text (preferred probes, success signals, stop conditions). This is prompt scaffolding sent to the model; nothing enforces it.

**Deterministic fallback.** On any bridge/provider error `requestNextControlAction` returns `deterministicNextAction` (`control-planning-service.js:103-112`), which replays the regex intent parser `planControlSteps` (`agent-control-planner.js:270-340`). So with no provider key the agent still clicks/types based on `/control click "X"`-style parsing. [inspected, high]

**Test hooks in production.** `globalThis.__resonantosNextActionOverride` and `__resonantosControlPlannerOverride` are honoured by shipped code (`control-planning-service.js:37-42, 61-85`; `side-panel-scheduled-browser-job-runner.js:72-74`), and `globalThis.__resonantosControlDwellMs` shortens the pre-click dwell (`content.js:500-505`). The override output still passes `sanitizeNextActionDecision`. These are the side panel's own window globals (extension origin), so a web page cannot set them; risk is limited to anything that can run script in the extension page. [inspected high; risk assessment hypothesis medium]

## Execution loop

**Who executes.** [inspected, high] The side panel page (`ext/side-panel.js`) owns the loop. `createControlStepExecutor` (`control-step-executor.js:30-88`) dispatches each step to side-panel helpers from `browser-page-actions.js`, which (a) choose the controlled tab (`activeTab` 137-165), (b) check the per-site permission mode (`sendContentAction` 327-338), (c) `chrome.tabs.sendMessage(tabId, message, {frameId})` to every frame returned by `chrome.webNavigation.getAllFrames` (245-268), and (d) if no content script answers, inject it with `chrome.scripting.executeScript({files: CONTENT_SCRIPT_FILES})` (270-289) or reload the tab (349-352). The content script performs the DOM action and returns a result object. The service worker (`background.js`) is not in the execution path; it only handles bridge config, side-panel open/handoff, and an advisory `action_request` reply (362-374) for which no sender exists in `ext/` (grep). `chrome.debugger` is not used anywhere in `ext/` (grep).

**Loop shape** (`agent-control-runner.js:458-875`), per iteration (default `maxSteps` 12; `runControlCommand` uses `max(12, seeded+8)` 921; scheduled runner uses 12 at 246):
1. Stop check (461) -> mark job `running` (465) -> overlay "reading" -> `observeControlPage()` (467) = `read_page` snapshot + readable tab list (`control-page-observer.js:25-41`).
2. `requestNextControlAction({goal, snapshot, history})` (471).
3. `done` -> `completionEvidenceForDoneDecision` (165-208): refuses "done" if the last action failed/needed approval or produced no visible change; otherwise archive report + `finishControlRun("completed")` (475-552).
4. `needs_approval` / `blocked` / no action -> terminal (`finishControlRun("approval"|"blocked")`, 553-568). Note: status "approval" here does **not** create a pending approval object.
5. Repeated same action after a no-change result -> blocked (571-629).
6. `appendControlStep` + overlay + last-instant stop check (630-654) -> `executeControlStep(step)` (655) -> stop check (656) -> post-action snapshot and `verifyBrowserAction` fingerprint compare (660-667).
7. If result says `approvalRequired` and boundary is `safe`, consult `taskConsentForStep`; if consent exists, re-execute with `{...step, userApproved: true}` (668-688). See Approval section for why this re-execution cannot succeed against the content-script gate.
8. Settle re-read after 650 ms if no change (690-705); one "precise-ref retry" when a text click matched exactly one visible ref and nothing changed (709-736).
9. Failure branch (760-828): every non-ok result is terminal `blocked`; `humanHandoff` or `public-submit` boundary -> phase `handoff`, message "click it yourself on the page, then resume or continue the job". No pending approval is ever created in the loop (comment 815-819).
10. Success -> step `completed`, sleep 350 ms, next iteration. Step limit -> `blocked-step-limit` (859-864).

**Content-script actuation** (`content.js`): clicks scroll the element into view, pulse the overlay, dwell 650 ms, dispatch `pointerdown/mousedown/pointerup/mouseup/click` events then `element.click()` (533-551). Typing uses `setNativeValue` on the resolved field (821) and, if `submit`, only `form.requestSubmit()` (846-859); synthetic Enter is never dispatched (comment 846-848).

**Scheduled jobs.** The live entry `controlCommandController.runControlCommand` always creates the job as `queued` (`side-panel-control-command-controller.js:218-224`) and calls `scheduler.tick()` (238). `browser-job-scheduler.js` starts up to `maxConcurrent` (default 2, 4) runnable queued jobs whose page locks do not conflict (84-97), and `side-panel-scheduled-browser-job-runner.js` builds a per-job runner instance and calls `continueControlLoop` (241-247). All jobs share one side panel, one controlled-tab pointer and one `withBrowserActionLock` (32, 38, 59), so "concurrency" is interleaving of observe/act steps across tabs, not parallel browsers. [inspected, high]

**The #240 "non-bypassable public submit handoff".** [inspected, high] `clickElement` (`content.js:507-559`) accepts `userApproved` in its signature but the body never reads it; the submit-like branch (519-532) is unconditional with an explicit comment "Do not add a userApproved or any other bypass gate here". The same holds for `typeIntoPage` (796-871). The runner treats a `humanHandoff` result as terminal `blocked` with phase `handoff` and never calls `setPendingApproval` with a non-null value in `continueControlLoop` (only `null` at 431). `approvePendingControlStep` (925-1078) still exists to drain **persisted legacy** approval objects: the only producers of a non-null `pendingApproval` in `ext/` are hydration from storage (`side-panel-browser-job-controller.js:125`) and the scheduled runner's sync of a value that the runner itself only ever sets to null (`side-panel-scheduled-browser-job-runner.js:91, 182-189`). The "Approve once" button in `monitor-renderers.js:884` is therefore reachable only for jobs persisted by an older build. [hypothesis: legacy path, medium-high]

**Consequence for "task consent".** The runner's `taskConsentForStep` re-execution with `userApproved: true` (`agent-control-runner.js:669-679`) can only ever be triggered when the content script returned `approvalRequired` for a step whose text classifies as `safe` (e.g. a `<button type=submit>Go</button>` inside a form). Because content.js ignores `userApproved`, the re-execution returns the same refusal and the step ends as a handoff. The consent store therefore never unlocks a content-script refusal; it only affects preflight skipping. [hypothesis, medium; the test "uses scoped task consent only for safe approval retries" at `test/agent-control-runner.test.mjs:373` uses a stubbed executor, so it does not contradict this]

**What the content gate does not cover.** Non-form, non-button, non-onclick elements (e.g. `<a href>` links, `<div>` without `onclick`, custom elements with click listeners added via `addEventListener`) with any label are clickable; a link "Post" or "Buy" is explicitly allowed (`content.js:458-465`, test "a plain navigation link with a commit-word is still clickable" `test/agent-control-public-submit.test.mjs:165`). Commit-verb matching is English-only (444). Clicks are dispatched to whatever element matched visible text; multi-match -> ambiguous refusal (569-577). [inspected, high]

## Stop / revoke / pause

- Commands (`app-command-handlers.js`): `pauseBrowserJob` 548-559 sets job `paused` (and finishes the focused run); `cancelBrowserJob` 635-647 sets `cancelled`; `resumeBrowserJob` 561-585 (only `paused|queued|failed`) sets `allowHumanStopOverride: true, status: "queued"` then `restartBrowserJob`; `continueBrowserJob` 587-611 restarts any non-running job from the current page. Monitor stop button shown for `running|approval|paused` (`monitor-renderers.js:280`).
- Enforcement is **cooperative polling**: the runner reads the job's status from the store before planning (461), immediately before `executeControlStep` (651-654, 675-678, 722-725, 1005-1012) and after it (656-659); `observeControlPage` throws if the job is paused/cancelled (`control-page-observer.js:26-31`); the scheduled runner refuses to execute a step for a paused/cancelled job (`side-panel-scheduled-browser-job-runner.js:59-69`). An in-flight content-script click/type cannot be interrupted once the message is sent. [inspected, high]
- Store-level protection: `updateJob` keeps `cancelled|paused` unless `allowHumanStopOverride` (`browser-job-store.js:775-778`); `finishControlRun` preserves a human stop over a stale runner completion (`control-run-state.js:180-185`); the scheduler keeps paused/cancelled when execution throws (`browser-job-scheduler.js:50-53`). #226 commits `6f4a51a`, `7e0ee00` added these.

## Jobs persistence and restart

- Storage: `chrome.storage.local` via an injected `storage` adapter; default keys `augmentorBrowserJobs`, `augmentorActiveBrowserJob`, `augmentorPendingSidebarPrompt` (`browser-job-store.js:428-430`); the live harness reads `augmentorBrowserJobs` directly (`test/agent-control-live.mjs:640, 691`), confirming the key in use. `persist` (581-589) writes **redacted durable records** (`redactTraceValue`), max 40 jobs (528), steps capped at 30 per job, artifacts 20 (167, 186). Preflight card persisted under `augmentorControlPreflight` (`side-panel-control-preflight-controller.js:9, 24-29`).
- Job record (`normalizeBrowserJob` 164-194): `id, goal, status (queued|running|paused|approval|completed|blocked|denied|cancelled|failed), planner, summary, artifacts, lastError, pendingApproval (only when status approval), preflightDecision, pageLock (only while queued|running|approval), timing, steps[{type,label,state,note,details,timing}]`.
- Page lock (`normalizePageLock` 147-162): `{type: tab|page, tabId, url, siteKey, acquiredAt, reason}`; conflicts by tabId, siteKey, or url (`conflictingActiveJobForLock` 707-717); `createJob` throws on conflict unless queued (734-738); the command controller cancels a conflicting job stuck in `approval` (`side-panel-control-command-controller.js:107-128`). If redaction altered lock routing fields, the durable copy drops the lock and demotes the job to `paused` (`durableRecord` 388-406).
- Restart: on side-panel load `loadBrowserJobs` hydrates and flips `running|approval` -> `paused` with `lastError: "Recovered after browser host reload..."` (`side-panel-browser-job-controller.js:34-43`; `recoverInterruptedJobs` 811-836). No automatic resumption. The side panel is the runtime, so closing the panel or the browser stops all jobs. [inspected, high]
- Resume path: `/resume` -> `restartBrowserJob(job)` = `runControlCommand(job.goal, {resumedFromJob: job})` (`side-panel.js:1113`) -> command controller re-queues the same job id (`createBrowserJob({existingJob,... status:"queued"})` 218-224; `side-panel-browser-job-controller.js:67-75` updates it in place) -> scheduler -> `runScheduledBrowserJob`, which seeds `localRun.steps` from the persisted job (84) **but calls `continueControlLoop({history: [], startIndex: 0})`** (241-247). The history-seeding variant (`agentControlRunner.runControlCommand` 877-923, `browserJobStepHistory` 21-44) is only reachable through `startControlCommand`, which is assigned at `side-panel.js:908` and never called. So the model restarts a resumed job without any memory of prior steps, even though the panel shows the old steps and `activateJobTab` re-focuses the locked tab (`browser-job-activation.js:8-22`). [inspected for both paths, high; "unreachable" relies on grep of `ext/` only, medium-high]
- Staleness: `staleBrowserJobEvidence` flags `running|approval` jobs with no step activity for 15 min (256-286) - advisory only; no status change (test at `test/browser-job-store.test.mjs:575`).

## Freshness (how it knows the DOM changed)

- No `MutationObserver`, no navigation listener in the runner. Freshness is re-observation: a fresh `read_page` snapshot before each decision (`agent-control-runner.js:467`) and after each action (661), a second one after 650 ms if nothing changed (690-705), and a fingerprint compare over title, url, first 1200 chars of text, and counts of controls/fields (`snapshotFingerprint` 130-142). A click that changes only a hidden state, or a page whose text is identical but whose controls changed in label (not count), is reported as "no visible page-state change" (156-161); conversely a ticking clock or ad rotation registers as "changed". [inspected high; failure modes hypothesis medium]
- Element refs are `data-resonantos-control-ref` attributes assigned lazily per page load (`content-control-refs.js:18-26`); a ref from a previous snapshot is resolved by attribute lookup (28-33) and only checked for still being a clickable candidate (`content.js:590-592`). After navigation the attributes are gone, so stale refs fail with "No clickable element matched ref". `switch_tab` clears the cached snapshot (`control-step-executor.js:51-52`); `onUpdated` in `background.js:274-281` only clears resonant-context snapshots, not control refs.
- Multi-frame: `read_page` merges frame snapshots (`browser-page-actions.js:259-261`); click/type are sent to all frames and the first `ok` wins, else the first `approvalRequired` (263-267).

## Coupling

- chrome.* APIs used by the control path: `chrome.tabs.query/get/update/sendMessage/reload` (`control-step-executor.js:20,45,50`; `browser-page-actions.js:140-161, 252, 350`), `chrome.webNavigation.getAllFrames` (246), `chrome.scripting.executeScript` for content-script injection (284) and the MAIN-world wallet probe (589-600), `chrome.storage.local` through an injected adapter (job store, preflight, site permissions), `chrome.runtime.onMessage/sendMessage` (content.js 1434; overlay 256-260), `chrome.sidePanel` in background. - Node coupling: the host service is Node (`fetch`, injected provider catalog); the extension code is browser ESM with no Node imports, which is why jsdom tests can load it. The bridge is the only link, over capability-token-protected HTTP (`bridge-server.mjs:123-128`).
