## 4. Architecture

Control flow for a sensitive action [inspected]:

1. Model emits a tool call (`src/agent/loop.ts`) -> `layerPort(session).call` (`agent-session.ts:43-63`) -> `Session.call` (`controller.ts:686-773`): tool spec and capability check (no `eval`/`devtools` in agent sessions), zod validation, tab resolution by ref, blocked-site check (`checkTabSite`), `MODAL_PENDING` if a dialog or a card is open on the tab, then the handler under a per-tab lock.
2. `click` (`tools/act.ts:64-142`): resolve and revalidate the ref -> actionability -> layer-2 preflight of the destination (`preflight.ts`) -> `gateTarget` -> `confirmGate`.
3. `confirmGate` (`gate.ts:163-336`): `classifyOn` asks the probe for `formFacts` (`probe/source.ts:644-728`) and, for Enter, Chrome's accessible name of the default button over `Accessibility.getPartialAXTree` (`gate.ts:60-71`); `classify()` is pure. Pay, grant and secret input throw `USER_STEP` in a `handover` session before any policy is consulted. Submit, delete and upload go to the host's `decideWrite` (`permissions.ts:41-48`: site rule, else mode). An `ask` opens a card through `host.prompt` -> `extension/layer.ts:32-46` route -> `PromptBroker.userPrompt().confirm` (`prompt-broker.ts:106-132`) -> panel event. The answer arrives on the panel port (`panel-port.ts:44-51`) -> `RunManager.handle 'answer'` -> `broker.answer`. After approval the target is resolved again and the site re-checked.
4. Dispatch (`pointer.ts`, `key-guard.ts`): trusted input via CDP `Input.*`; an in-page guard in the isolated world re-applies the hit rule on the trusted press and cancels the sequence if anything else would receive it (`source.ts:914-964`); for keys, each unit is checked and the release of Space or Enter is judged again (`key-guard.ts:202-243`).
5. Receipt records `sensitive`, `confirmedByUser`, `allowedBy` (`act.ts:144-152`, `text.ts:134-167`); every call and every card is audited (`controller.ts:761-772`, `gate.ts:274-282, 300-308`).

What the content script can and cannot do. There is no content script in the Alpha sense. The only in-page code is the probe, a string evaluated once per frame document in an isolated world created with `grantUniversalAccess: false` (`probe-client.ts:49-62`); it reads DOM facts and arms event guards; "it never computes accessible names" and "the probe never decides the category" (`source.ts:1-2, 33`). The page cannot call it, see it or replace its prototypes (separate JS world); the probe reads form properties through the prototype so a control named `action` cannot shadow them (`source.ts:259-261`). The decision, the dispatch and the card are all in the service worker; the card's site is read from `chrome.tabs.get`, never from page text (`gate.ts:198-199`, `prompt-broker.ts:22-23`).

How a malicious page can still influence the classifier [inspected, reasoning from code]:
- Naming from the start. The inputs are the element's accessible name, its classes and test IDs, its form ownership and submitter type, and a money amount in the element or its parent. A page that labels its payment control "Show details", gives it `type="button"` with a JavaScript handler, no form owner and no amount nearby, is `null` (`classify.ts:175-187`): no card in Ask mode, dispatched in Auto mode. The gate defends against a target that changes during the action (`TARGET_CHANGED`), not against one that lied before it. This is the "detection is best effort" clause.
- Language. Vocabulary is English and Chinese; other languages rely on the structural facts alone.
- Site key granularity. Rules and the blocked list are keyed by exact host (`url-policy.test.ts:101-113`: `mail.example.com` is allowed when `example.com` is blocked), so a redirect to a sibling subdomain escapes a Block rule; the allow and deny lists of the test panel match subdomains (`url-policy.ts:64-69`), the product's blocked list does not. The choice is deliberate upstream (`site.ts:1-3`), but for Block and Ask it is a silent bypass of a configured control, not a least-surprise choice (S-nanobrowser-2, accepted): the port must not copy it (section 7).
- Governance and wallet actions (added in review, D-nanobrowser-1). The classifier has no vote, delegate, sign, connect-wallet, claim or stake category (section 3, item 6). An injected model in Auto mode, or on a site with an Allow rule, can submit an off-chain advisory vote form, and in any mode can click a JavaScript "Claim" or "Delegate" button that classifies `null`. On-chain signing has a backstop outside Nanobrowser: a wallet's own popup is a `chrome-extension://` page, which the navigation policy refuses whatever the lists say (`url-policy.ts:34-44`) [inspected]; whether an agent session could be handed a wallet popup window as a shared tab was not established.
- Sibling effects while a card waits (`discovery-s2-br-e.jsonl` line 109, arXiv 2607.14166 "Stop Means Stop", the "sibling leak"). Within one conversation, mutating calls run one at a time and only consecutive reads run in parallel (`agent/loop.ts:1012-1036`), so a pending card holds the conversation's next mutation; a second card on the same tab gets `MODAL_PENDING` (`controller.ts:715-722`). Conversations on other tabs are gated independently [inspected; not tested for a sibling leak in CI].
- Approval fatigue. "Always allow on this site" on a write card writes a permanent `allow` rule (`prompt-broker.ts:129-130`, `permissions.ts:50-54`); and the mode chosen in the composer becomes the default for new conversations (`run-manager.ts:554-559`, commit `4befe5a`/`64a5e11`), so one Auto choice persists.
- The model's `intent` text is printed on the card (`gate.ts:257`); an injected model can write a soothing intent, but category, target, reason, frame host and destination host come from the layer.
- What the page cannot do: reach the worker (no `externally_connectable`, panel port restricted), alter the probe, approve a card, change the policy (no protocol call changes `urlPolicy`, `confirmPolicy`, `handover` or capabilities: `controller.ts:507-536, 560-564`), or make the model run page script.

Storage: IndexedDB (`idb`) for conversations and blobs; `chrome.storage.local` for settings, providers, API keys (`nb.keys`, plaintext in the extension's storage, `settings.ts:118-119`) and site rules; `chrome.storage.session` for live model pairs. Runtime: TypeScript 6, React 18, WXT 0.21, Vite 8, Node 24 and pnpm 10 to build. Lifecycle: worker restart restores unfinished runs and reopens the pending card with a new id; nothing runs without an answer (`run-manager.ts:313-372`); Cancel on Chrome's debugger bar is Stop (`run-manager.ts:135-140`). Identity: none; one user, one browser profile. Operational model: embedded in the browser; nothing outside the extension can drive it (AGENTS.md:25, 57).

OSC-20 (regression counted as pass): the scenario harness has typed pass/fail per scenario (`outcome(...)` in `scenarios/registry.ts`), but it is not a CI gate either. OSC-18 (planner never exercised): Nanobrowser's real-model evaluation exists but is manual; same gap, more honestly labelled.

Threat T1 is narrowed, not closed: an injected model can still perform any action the classifier calls `null`, and in Auto mode any submit/delete/upload. What a host-side (native) checkpoint would have to add: (a) an approval record the bridge requires before a privileged route runs (R11, seam 3), so that a compromised or replaced extension cannot self-approve; (b) a second classification input independent of page labels (the request itself: method, destination host, body size, presence of credential-shaped fields), checked where the request leaves the machine, since the extension's network guard today covers navigation documents only, not XHR/fetch form posts; (c) policy storage outside `chrome.storage` so a page or add-on with extension privileges cannot rewrite rules; (d) vocabularies for the languages the project serves; (e) added in review (D-nanobrowser-1): a governance and wallet category (vote, cast, delegate, sign, connect wallet, claim, stake) that is a user-only step like pay and grant, since interaction I4 counts voting and signing as human-only and Phase 1 advisory votes are plain web forms with no wallet popup (`dao-requirements.md` section 5 item 6); (f) added in review (S-nanobrowser-2): Block and Ask rules that match the registrable domain (Public Suffix List) and every subdomain, Allow by exact host; (g) for T22, a ceremony rendered by a component with no agent code that constructs the approval record from the canonical action (X-4; deferred by the lead to Gate 3, state.md D3.7).

R29: see section 12 (feature coverage versus the A and B rows) and section 7.

## 6. Reuse decision

Learn the pattern and reimplement, plus vendor a limited component: the pure parts of the layer (`classify.ts` with `classify.test.ts`, `url-policy.ts` with its tests, `text.ts` with `boundary.test.ts`, the `gate.ts` ordering: classify -> protected steps -> host policy -> card -> re-resolve -> site re-check) are import-isolated (AGENTS.md:89: nothing under `src/browser-control/` imports from outside it) and small enough to port. Do not adopt the extension as a dependency: it is a product with no library surface, no external entry point by design, one maintainer, and a two-day-old release. Do not fork the whole extension: the Alpha's bridge, archive and delegation have no counterpart in it and the maintainer's stated scope excludes an MCP or bridge client for now.

Why it beats the alternatives in section 12 for this slice: it is the only MV3 extension among them with a per-action ceremony enforced before dispatch, a network-level navigation block and a written injection corpus; browser-use and Playwright MCP are Python or Node processes without a ceremony; Intact and Progent are academic harnesses in Python.

Hard gates:
- G1 pass: no cloud service for the core function; analytics optional and absent from development builds (`.env.example`, PRIVACY.md); local models supported.
- G2 pass: the extension runs identically on Windows, macOS and Linux (Chrome MV3); the developer lane's Chrome finder covers macOS and Linux only (`find-chrome.mjs:18-29`) and fails loudly on Windows without `CHROME_PATH`. No silent no-op found.
- G3 pass: Apache-2.0 file-level; all runtime dependencies Apache-2.0, MIT or ISC (`licences.ts`).
- G4 N/A (no chain).
- G5, amended in review (S-nanobrowser-3, D-nanobrowser-1). Upstream artifact as is: **fail** for the human-only clause outside its categories. Within its categories, pay, grant, secret input and prompt dialogs are the user's in every mode of an agent (handover) session and no model call can change that (`gate.ts:178-197`, `controller.ts:507-536`); but I4's human-only set includes voting and wallet signing, which the classifier does not know (section 3, item 6), so an off-chain advisory vote is at best `submit` (dispatched in Auto mode or under an Allow rule) and a JavaScript "Claim" or "Delegate" is unclassified. I4 ("enforced at the bridge, not in UI", interaction.md:78) is not met either, since enforcement is in the extension's worker. Recommended pattern port: **pass only with three blocking conditions**: (1) an R11 host-side approval record that the bridge requires for submit, pay, grant and governance-class routes; (2) a governance and wallet category that is a user-only step (section 5, item e); (3) acceptance case 3(b) of section 11 (neutrally labelled payment control) and the governance fixtures run as required cases. I1 and I2 are untouched (no DAO code). The reuse decision does not change (adoption was already rejected; the port carries the conditions), Under lead ruling D3.13 (3), G5 is judged on the decision as proposed, so the verdict is a pass with these conditions, with the upstream-as-is fail reported beside it.

## 7. Integration design

Alpha seam: os-map section 17, seam 3 ("make human approval a core-visible event") with the extension-side changes of section 11.

Boundaries: keep Nanobrowser's split. Extension side: a worker-resident gate module (port of `gate.ts` ordering and `classify.ts`) that every page action passes through before any `chrome.tabs.sendMessage` or `chrome.scripting.executeScript`; site rules keyed by `siteOf`; the card answered only over a port from the extension's own panel URL. Bridge side (Node 24): the bridge cannot call Nanobrowser code (browser-only TypeScript using `chrome.*`; no library, WASM or sidecar form exists); what crosses is a data structure, the `ConfirmRequest` shape (`ports.ts:122-145`: id, tabId, category, action, target, origin, site, frameHost, destinationHost, intent, reason, canRemember) plus the answer and the receipt's `sensitive/confirmedByUser/allowedBy` fields. The bridge stores the approval record and privileged routes (public submit, promotion, delegation start) require its id.

Identity semantics: Nanobrowser has none; the Alpha's principal (R01) must be added to the request record by the bridge, not by the extension.

Error behaviour to copy: typed codes with a `delivered` flag (`text.ts:124-132`: "nothing dispatched; safe to retry" versus "input was delivered; do not retry blindly"); `NEEDS_USER` when no prompt handler exists; a late answer has no effect.

## 8. Security and governance effects

- New privileges if adopted whole: `chrome.debugger` on `<all_urls>` (Chrome shows a "started debugging this browser" bar; Cancel detaches and is treated as Stop), `webNavigation`, `scripting`. If only the pattern is ported, the Alpha's permission set does not grow. Blast radius (added in review, S-nanobrowser-4): `chrome.debugger` on `<all_urls>` gives full CDP over every attached tab (cookies, storage, network bodies). In the Alpha, where content-script add-ons share extension privileges (OSC-30) and keys and tokens sit in `chrome.storage.local` (OSC-06), vendoring the layer would turn any extension compromise into a full browser-session compromise (A4). Vendoring is acceptable only after R21 isolates add-ons from the worker that holds the debugger; the pattern port does not need the permission.
- Attack surface: a page's only way in is its own DOM; the classifier's inputs are page-controlled (see section 4), so the residual T1 path is a mislabelled control or an unlisted language. The worker trusts its own panel over a URL-checked port (`panel-port.ts:12`); anything with extension-level privilege (the Alpha's content-script "add-ons", OSC-30) would also be able to answer cards: isolation of add-ons (R21) is a precondition for the gate meaning anything in the Alpha.
- Revocation: Stop aborts the run and withdraws every card (`run-manager.ts:193-198`); blocking a site applies to every open session at once (`run-manager.ts:142-146`); a changed site rule takes effect at the next classified write. No per-principal grants.
- Isolation: probe in an isolated world; agent sessions have no page script, no devtools, uploads from attachments only; secrets masked in results, prompts and audit. Keys stay in `chrome.storage.local` in clear (extension-sandboxed, not OS-vault) and go only to their provider [inspected `settings.ts:118-119`; reported PRIVACY.md].
- Personal data flows: page text, attachments and screenshots go to the chosen provider; daily counts to PostHog US unless switched off (PRIVACY.md:20-25). No Nanobrowser server, no account.
- Custody and trust in maintainers: one maintainer signs every release; no reproducible build; Web Store distribution. Trust placed is high for an adopt decision, low for a pattern port.
- Counterexample rows (section 3 of the brief), answered:
  - s2-br-e against R19: (1) no measured injection success rate or corpus run: confirmed (section 5); (2) real-model eval manual: confirmed (`eval.ts:1-7`); (3) rewrite days old: confirmed (`8ac395d` 2026-10-13); (4) permission set as broad as the Alpha's: confirmed and broader (`debugger`); (5) classify.ts English-only unknown: refuted in part, English and Chinese, nothing else (`classify.ts:17-90`).
  - `discovery-s2-br-e.jsonl` line 109 (arXiv 2607.14166; not an `against` row; the "sibling leak" paper's lesson for R19/R11): no sibling leak within one conversation, since mutations run sequentially and a pending card holds the next one (`agent/loop.ts:1012-1036`, section 4) [inspected]; no test asserts it; add it to the port's tests.
  - s2-br-h against R29/R19: "replaces one in-extension gate with another": confirmed as to location (worker, not bridge), refuted as to class: the Alpha's gate is DOM heuristics in the side-panel page and content script, bypassable by `tabs.sendMessage`, with no per-action card and no navigation block; Nanobrowser's is worker-resident, not reachable from pages, with a per-action card and a network-level block. Same trust domain (the extension), different trust class within it. The quotes are accurate and the Auto-mode clause is correct (`settings.ts:237-240`).
- Friction: one card per classified write in Ask mode; hand-overs for pay, grant, secret input and prompt dialogs; the debugger bar on every tab the agent works in.
