## 4. Architecture

Control flow for one request [inspected `src/gate/gate.ts:448-1454`]:

1. Raw-path parse; reject `..`, `.` and their percent-encodings, and null bytes (469-507).
2. `/_aegis/health`, `/_aegis/stats`, `/_aegis/metrics` answered before any authentication (509-535). Stats are ledger totals; the test "stats endpoint is accessible without agent token" (`gate-agent.test.ts:234`) locks this in.
3. If `requireAgentAuth` (default true, `gate.ts:153`): read `X-Aegis-Agent`, hash it, look it up in SQLite (`agent.ts:118-125`); 401 if missing or unknown (537-612).
4. Per-agent concurrent-request cap, default 50 (614-655).
5. `vault.getByService(<first path segment>)`: a fresh SQLite read and AES-GCM decrypt on every request (`vault.ts:337-354`); 404 if none.
6. Credential TTL (701-733), method scope (735-774).
7. Grant check `agentRegistry.hasAccess(agent.id, credential.id)`: one SQLite `SELECT` per request (`agent.ts:224-230`; `gate.ts:776-814`); 403 if absent.
8. Policy evaluation and rate limits (816-1095).
9. Target host = `X-Target-Host` header or the credential's first domain; domain guard (1097-1141).
10. Build outbound headers, inject secret (1143-1161).
11. Buffer the whole request body (cap 1 MiB, 1171-1213), run body inspection (1222-1269).
12. Circuit breaker (1271-1296); `https.request` to `targetDomain:443` (1305-1314), retry GET/HEAD/OPTIONS on 502/503/504; delete `set-cookie` from the response (1346-1348); write the audit row; `proxyRes.pipe(res)` (1350-1381).

Storage: one SQLite file per vault under `.aegis/` (tables `credentials`, `credential_history`, `audit_log`, `agents`, `agent_credentials`, `webhooks`, `users`; `src/db.ts:147-240`). Master key from env `AEGIS_MASTER_KEY`, config file `vault.master_key`, or the OS store, in that order (`src/config.ts:455-459`).

Identity model: agents (bearer tokens in a custom header), users with RBAC roles for the CLI (`AEGIS_USER_TOKEN`, `src/cli/auth.ts`; bootstrap mode allows everything until the first user exists). Grants are rows, not tokens: no attenuation, no delegation, no grant expiry; credential TTL is per credential, not per grant [inspected].

Lifecycle: `Gate.start()` / `stop()`; stop refuses new requests with 503, drains in-flight requests up to `shutdownTimeoutMs` (10 s) and then `closeAllConnections()` (`gate.ts:368-432`; tests "stop() waits for in-flight requests to drain" 1520, "forces shutdown after timeout with active requests" 1658). Rate-limit windows are in memory and reset on restart (THREAT_MODEL D-1 residual) [inspected].

Operational models: embedded library (the `Gate` class), sidecar CLI process (`aegis gate`), MCP server spawned by an MCP host, Docker image.

## 5. Direct relevance

R03 (secret brokering). Alpha seam: the key reaches children at `browser-first/host/addon-delegation-service.mjs:1776-1779` (`OPENAI_API_KEY` and `RESONANTOS_HERMES_API_KEY` set from `runtimeProvider.apiKey`) and, for OpenCode CLI, through `scopedHermesEnv`-style allowlists that include provider env keys (`:1599-1625`); DSH gets `DEEPSEEK_API_KEY` (OSC-36, `dsh-runtime.mjs:27`) [inspected in the Alpha clone at 578fbbc]. The bridge itself already holds keys in memory and speaks only OpenAI wire format (`provider-bridge-service.mjs:1260-1274`; OSC-15, OSC-16; os-map 6) [inspected]. Aegis's pattern (child gets a base URL and a revocable token; the broker injects the key) is exactly the missing component. The Hermes adapter builds its client from `RESONANTOS_HERMES_BASE_URL` and `RESONANTOS_HERMES_API_KEY` (`addon-delegation-service.mjs:1649-1659`), so the base-URL half of the swap is trivial.

R01 (per-principal grants). Aegis covers only credential grants for outbound API calls. It does not touch the bridge's 26 route capabilities (os-map 5.3, 13; OSC-02, OSC-43..46) and has no attenuation, expiry or offline-verifiable token. It is relevant to R01 only for the sub-case "which delegated child may spend which provider key".

Threats: T2 is partly closed (key not in child env; still open to a same-user child with a shell, section 8). T9 is improved at rest (encrypted vault plus OS key store, versus the Alpha's choice between losing keys on restart and plaintext env). T3 is not closed and gains a new surface (all-interface bind, unauthenticated stats and dashboard). T10 is touched: Aegis also relays upstream error bodies unredacted (`gate.ts:1380-1381`; THREAT_MODEL I-2 residual at `docs/THREAT_MODEL.md:315`).

## 6. Reuse decision

Decision: learn the pattern and reimplement (in the bridge's code, on a broker channel separate from the bridge's main listener; amended for X-5, section 7). Unchanged by the 2026-10-21 review round, as are all hard gates. Keep Aegis as the reference design and its tests as a checklist; do not adopt it as a dependency or sidecar now.

Why this beats the alternatives:
- Adopt or wrap as a sidecar would add a second HTTP service with its own token scheme next to the bridge's 26 tokens, bound to all interfaces, with a header that Hermes's OpenAI client does not send, default body inspection that refuses normal chat payloads, a native SQLite addon that the Alpha bridge (dependency `undici` only) does not carry today, and a single maintainer with no commit in 75 days. Each is fixable with a small patch, but together they mean a fork.
- Vendor a component: the reusable pieces are small (`injectCredential`, the header-strip list, `domainMatches`, the per-request grant lookup). Copying the ideas costs less than tracking the upstream.
- The bridge already holds the keys and already speaks the wire format. The missing part is a scoped token per delegation, a forwarding route that injects the key, an audit row per call and an abort of open streams on revocation, which the Alpha already does for its OpenCode proxy (`test/opencode-execution-revocation.test.mjs` "off closes live SSE before settings acknowledgement") and Aegis does not.

Compared with section 12's competitors: greyproxy and terok-sandbox lack Windows; oidc-agent brokers OIDC tokens, not API keys; Infisical agent-vault is designed for a separate machine. Aegis is the closest fit in language and model, which is why its pattern is the one to copy.

## 7. Integration design

Target: a bridge-internal broker, Aegis-shaped, using Alpha files.

- Process boundary and transport (amended for security review S-getaegis-aegis-1 and X-5; threat model v0.2 Containment row: "the broker channel is not the bridge's main listener and is the only bridge surface a confined child can reach"): the broker must not be a route on the bridge's main loopback listener. Granting a confined child that port would grant every open proxy prefix on it (OSC-05) and contradict the R02 candidates, which deny loopback (Convira's AppContainer child is refused loopback, convira dossier line 232; srt's Linux child has its own netns). The broker is a separate listener or channel that serves only the broker route: a Unix socket bind-mounted into the child on Linux and macOS, and on Windows a named pipe or loopback listener that the containment layer grants by name. Which transport, and whether the broker is a separate low-privilege process, is a Gate 3 architecture decision (state.md D3.7, X-5); until it is made, the first PR below is written against an abstract `listen(transport)` and must not register on `bridge-server.mjs`. Children get `OPENAI_BASE_URL=<broker transport URL>/broker/<delegationId>/v1` and `OPENAI_API_KEY=<scoped delegation token>`. Unlike Aegis, the broker accepts the scoped token in `Authorization: Bearer`, so Hermes, OpenCode and any OpenAI SDK work unchanged; the broker then replaces that header with the real key.
- Data structures: `{ delegationId, principal: { kind: 'hermes'|'opencode'|'dsh', addonId }, providerRouteId, allowedHosts, expiresAt, revokedAt }` in a `Map` keyed by the SHA-256 of the token (Aegis `agent.ts:118-125` pattern), plus a `Set<AbortController>` per grant for open upstream requests.
- Per-request checks, in Aegis's order: token, grant not revoked or expired, route resolved by the bridge (never by a child-supplied host; drop Aegis's `X-Target-Host`), strip `authorization`, `x-api-key`, `proxy-authorization`, `host` (Aegis `gate.ts:1143-1153`), inject, forward with `fetchProviderResponse` (`provider-bridge-service.mjs:1260-1280`), audit row with the delegation id.
- Revocation: delegation end, cancel and execution-settings off call `revokeGrant(delegationId)`, which marks the grant and aborts every controller in its set, so in-flight streams end (the property Aegis lacks; threat model v0.2 T4 and Authorization row, security review X-7). The bound is one chunk after revocation. Client disconnect also aborts the upstream request (Aegis does not, section 8).
- Error behaviour: 401 bad token, 403 revoked or expired, 502 upstream failure with a fixed body; do not relay provider error bodies verbatim (fixes the T10 note at `provider-bridge-service.mjs:1294` for this path).
- Reflection (amended for S-getaegis-aegis-2 and X-8; threat model v0.2 T2 and Secrets row): inject the key into headers only, never into the body or URL, and pass every byte relayed to the child (2xx body, SSE chunks, error body, response headers) through a redactor that replaces the exact key string, and its base64 and URL-encoded forms, before writing. For SSE the redactor keeps a carry-over of key length minus one bytes so a key split across chunks is caught. This is the response scanning Aegis lists as future work (`docs/THREAT_MODEL.md:314`).
- Security state (threat model v0.2 T21): grants and the token-hash map live in bridge memory and the audit rows in the bridge-only store that Gate 3 decides (X-1); nothing a child can write holds a grant.
- Identity: the delegation id travels into the audit row and the existing delegation artifact, so the originating principal survives.
- Alpha files that change: `browser-first/host/addon-delegation-service.mjs` (1755-1790 Hermes env; the OpenCode CLI env near 2221-2316); a new `browser-first/host/provider-broker.mjs`; `browser-first/host/provider-bridge-service.mjs` (export a forward helper); `browser-first/host/bridge-server.mjs` only to start and stop the broker's own listener (amended: no broker route on the main route table, and the broker listener carries no other route; os-map 5.3); `browser-first/host/dsh-runtime.mjs:27` later.
- Tests that change among the 2,424 browser-first tests: `test/addon-delegation-service-error-handling.test.mjs` "Hermes MiniMax execution uses OpenAI-compatible custom runtime endpoint" (asserts `env.OPENAI_API_KEY === "session-minimax-credential"` at 1202-1203; must invert) and "OpenCode provider matrix scopes explicit provider environment keys" (1429); `test/bridge-route-capability-audit.test.mjs` (every new route must declare a capability, os-map 5.2; amended: it should also assert that no `/broker` prefix exists on the main listener); `test/dsh-native-credentials.test.mjs` when DSH moves. `test/provider-route-acceptance.test.mjs:117-128` stays valid (keys still never reach the extension).
- If Aegis were used as a sidecar instead: patch `Gate.start()` to bind `127.0.0.1`, accept `Authorization: Bearer aegis_...` as the agent token, set `bodyInspection: 'off'` for model credentials, and pass a port in the domain allowlist through to `https.request`. Four upstream PRs or a fork.

## 8. Security and governance effects

- New privileges: the broker holds every provider key and the right to spend it; it must be at least as protected as the bridge.
- Attack surface added by Aegis as shipped [inspected]:
  - The Gate binds all interfaces: `this.server.listen(this.port, cb)` with no host (`gate.ts:315`); Node then listens on `::`/`0.0.0.0`. The dashboard does the same (`dashboard-server.ts:183`). Only the MCP HTTP transport binds `127.0.0.1` (`mcp-server.ts:961`). There is no option to choose the bind address (amendment grep, section 5 Component surface row). The CLI prints "any localhost process can use credentials" for `--no-agent-auth` (`src/cli/commands/gate.ts:30, 177`) when in fact any host on the LAN can, over plaintext HTTP unless `--tls`. With agent auth on, a LAN host can reach the unauthenticated `/_aegis/stats`, `/_aegis/health` and (when enabled) `/_aegis/metrics`; it can capture `X-Aegis-Agent` tokens in cleartext only when agents reach the Gate across the network (Docker image, remote agents), since loopback traffic from a local agent does not cross the LAN (amended: the first run said a LAN observer can capture tokens without that condition). This is the os-map 5.3 LAN finding reproduced by default, not by opt-in, and a listener of the kind the v0.2 Component surface property excludes (security review X-6).
  - The dashboard API (`/api/credentials`, `/api/agents` with grants, `/api/requests` audit rows, `/api/users`) has no authentication and sends `Access-Control-Allow-Origin: *` (`dashboard-server.ts:236-239, 255-290`), so any web page the user visits can read the audit trail and credential metadata while `aegis dashboard` runs (V1). No secrets are returned (`dashboard.test.ts:595, 612`).
  - `/_aegis/stats` is unauthenticated on the Gate (`gate.ts:516-522`).
  - With agent auth on, web pages cannot use the Gate: `X-Aegis-Agent` is not a CORS-safelisted header and the Gate sends no CORS headers, so no-cors requests cannot carry it [inspected + browser rule]. With `--no-agent-auth` (the README quick start), a page can fire no-cors POSTs that spend credits.
- Same-user child (V3) [inspected]: the THREAT_MODEL trusts the machine (`docs/THREAT_MODEL.md:43-50`) and accepts same-user debugger access (`:570`), but rates the master-key-on-store residual "Low" (`:331`). On Windows any same-user process can call `CredRead` on `aegis/master-key`; on Linux any same-user process can call `secret-tool lookup` once the keyring is unlocked; on macOS the item is added by the `security` tool, which is then trusted to read it back without a prompt [hypothesis for macOS ACL behaviour]. With the master key and the `.aegis` directory, every credential decrypts. Aegis therefore protects keys from an agent that only speaks HTTP, not from an agent with a shell, which is what Hermes, OpenCode and DSH are. R02 containment (or a dedicated OS account for the broker) is a precondition for the T2 claim.
- Grant minting by a same-user process (threat model v0.2 T21, T22) [inspected, amendment]: CLI RBAC allows every command until the first user exists (`src/cli/auth.ts:28-29`), `aegis init` creates no user, and the grant tables sit in the `.aegis/` SQLite file; a same-user agent with a shell can run `aegis agent grant` in bootstrap mode, or open the database with the master key from the OS store after RBAC is enabled. The comment at `auth.ts:16-17` says `aegis init` creates the first admin; the code does not, and `docs/USAGE.md:337-340` gives the correct sequence. Same precondition as the next bullet: R02 or a separate OS account.
- Secret on argv at init: Windows `cmdkey /pass:<master key>` (`credential-manager-windows.ts:79-83`; `setKey` at 79, the `execFileSync('cmdkey', [..., '/pass:${key}'])` call at 81; amended for A-getaegis-aegis-1) and macOS `security add-generic-password ... -w <key>` (`keychain-macos.ts:44-46`) put the master key on a command line visible to same-user process listings for the life of the call; Linux uses stdin (`secret-service-linux.ts:42-44`). The authors list this as further hardening (`THREAT_MODEL.md:559`).
- Revocation story: grant removal, agent removal and token regeneration take effect on the next HTTP request; no in-flight termination except stopping the Gate (10 s drain, then force close). Client disconnect does not abort the upstream request (no `res.on('close')` abort of `proxyReq`), so a cancelled delegation can keep spending until the upstream finishes [inspected `gate.ts:1304-1447`].
- Echo (threat model v0.2 T2, security review X-8): the Gate relays upstream bodies unredacted (`gate.ts:1380-1381`); an upstream that echoes the injected header or URL hands the key to the agent. Authors' residual: Medium (`docs/THREAT_MODEL.md:315`).
- Isolation story: none at OS level, by design.
- Personal data flows: request paths and agent names go to the local SQLite ledger; optional webhooks send block events to admin-configured URLs.
- Custody and trust in maintainers: one maintainer publishes npm with a provenance fallback that silently drops provenance if attestation fails (`release.yml:98-101`). A dependency on `@getaegis/cli` would trust one person's npm token.
- Friction: `aegis init` key ceremony, agent token handling, optional Shamir unseal (`src/vault/shamir.ts`, `seal.ts`).

## 12. Recommendation and confidence

Benefits of the Aegis pattern: the child holds a revocable token instead of a provider key; every call is checked against the database and audited with the agent's identity; keys can be encrypted at rest with the master key in the OS store, which answers ADR-022's deferred vault for T9. Trade-offs as shipped: all-interface bind, unauthenticated dashboard with `*` CORS, custom auth header, HTTPS-443-only upstream, over-eager default body inspection, no in-flight revocation, no redaction of echoed credentials, bootstrap-mode RBAC, no defence against a same-user child with a shell. The amendment round changes neither the decision nor any hard gate; it changes where the reimplemented broker listens (section 7: not on the bridge's main listener, transport pending the Gate 3 decision on X-5) and adds header-only injection with response redaction. Blockers to adoption: those defects plus a single steward with no commit for 75 days. Readiness: v1.0.5, usable for experiments; not ready as a trust-boundary dependency.
