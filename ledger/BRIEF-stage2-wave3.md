# Stage 2 Wave 3 briefs: language agents and provenance agent (lead, 2026-10-20)

Each Wave 3 agent reads `BRIEF-stage2-common.md` first, then its section here. Language agents cover all 30 requirements on their regional platforms (master prompt section 4.2) and run native terms on the global platforms (section 4.1). They start after the branch agents have reported, so the lead's launch message lists the candidates already found; a language agent's job is to find what the English branches missed, confirm which copy of a mirrored project is canonical, and read non-English documentation that the branches could not.

## Language agent common rules (s2-lang-zh, s2-lang-fr, s2-lang-de, s2-lang-nl)

1. Read your glossary (`glossary/<lang>.md`) in full: Table 2 gives ready search strings per requirement; the platform-notes section tells you which endpoints work anonymously and which are closed; the rejected-terms section tells you what not to search. Read `lessons/regional-platform-access.md`.
2. Read the branch ledgers that exist in `ledger/discovery-s2-br-*.jsonl` (they are JSONL; use `python -I` to list `canonical_source_url` per `requirement_id` rather than reading whole files). Do not re-record a codebase a branch already has unless you add a new source record for it (a regional mirror, a native-language paper, a non-English design document) or you can show the branch's canonical URL is wrong; in that case write a row with `disposition: duplicate` naming the branch row and put the correction in `notes`.
3. For every requirement, run at least two native-language queries on each regional platform that is open to you and at least one native-language query on GitHub. Record every query, including empty ones, in your negative ledger.
4. Where the glossary says practitioners keep the English word, search the English word on the regional platforms; that is still language-agent work because the regional platform is the point.
5. Canonical-copy check: for any project with both a GitHub and a regional (Gitee, Framagit, openCode, university GitLab) presence, record which one has the newer commits, the issues and the releases, and set `canonical_source_url` accordingly. Note it in `duplicates_or_mirrors`.
6. Quote, then translate: key claims from non-English documentation go in `notes` as original text plus English translation, `[MT]` if machine translated.
7. Documentation language and the presence of an English-speaking maintainer community go in `maintenance`, never into `disposition`.
8. Disconfirmation task as in the common brief, applied to your three to five strongest new candidates.
9. Output: `ledger/discovery-<id>.jsonl` and `ledger/negative-<id>.jsonl` only. Time box 150-250 tool calls; stop when two sweeps add little, and say so.

## s2-prov (provenance and deduplication agent)

Purpose: turn thirteen ledgers (eight branches, four languages, one probe) into one list of unique codebases and one coverage matrix, so the lead can find thin cells for pass 2 and build the Gate 2 longlist.

Inputs: every `ledger/discovery-*.jsonl` and `ledger/negative-*.jsonl`; `ledger/SCHEMA.md`; `stage1/gaps.md` (requirement list and branches); master prompt section 4 platform lists as reproduced in `BRIEF-stage2-common.md` section 4.

Method:
1. Validate every ledger row against SCHEMA.md with `python -I`; list malformed rows per agent in your report (do not fix them; the lead sends them back).
2. Group source records into codebases. Two records are one codebase when they share a canonical source, or when one is a package, paper, archive snapshot or mirror of the other (follow `duplicates_or_mirrors`, repository fields in package metadata, and paper code links). A fork is a separate codebase only when its changes alter the architecture or the reuse decision; say which in notes.
3. Write `ledger/codebases.jsonl`, one row per codebase: `codebase_id` (slug), `name`, `canonical_source_url`, `requirement_ids` (array), `branches` (array of agent ids that recorded it), `source_records` (array of result_url), `platforms` (array), `languages_found_in` (array of search languages), `project_doc_language`, `upstream_status` (the most conservative status recorded), `license_code`, `license_flags` (copyleft, source-available, NOASSERTION, dual, "MIT plus restriction"), `chain` (solana, evm, agnostic, none, n/a), `commit_sha_or_swhid`, `latest_version`, `maintenance_summary`, `tests_summary`, `counterexamples` (array of notes from counterexample rows against it), `evidence_level` (best level among its records), `disposition_summary` (candidate / lead / excluded / counterexample-only), `dedup_notes`.
4. Write `ledger/coverage-matrix.md` with: (a) one row per platform from sections 4.1 and 4.2 (plus `web`, `university-gitlab` and the JA/KO platforms): purposeful searches (count from both ledgers), languages searched, unique codebases after dedup, candidates (disposition candidate), notable false positives, limitations (blocked, paywalled, metadata-only, defunct, rate-limited, substituted as with Papers with Code); (b) a second table language x requirement with counts of unique codebases and a mark for cells with zero searches (unexplored) versus zero results (searched, empty); (c) a third table requirement x branch with candidate counts; (d) a list of the thin cells you see (requirement with fewer than two candidates; platform with zero purposeful searches; language x requirement cells unexplored).
5. Record the JA/KO probe decision in the coverage matrix as the master prompt requires (section 5.6), quoting the probe's Decision section.
6. Do not judge fitness; that is the lead's job. Do flag records where two agents disagree about canonical source, licence or status.

Output files (the only files you may write): `ledger/codebases.jsonl`, `ledger/coverage-matrix.md`, and optionally `ledger/prov-validation.md` for the malformed-row list and the disagreement list if they are long. Time box 80-150 tool calls. Return message: counts (records in, codebases out, candidates, leads, excluded, counterexample-only), malformed rows per agent, disagreements, the ten thinnest cells, file paths.
