# Threat model draft (lead, v0.2.2, 2026-10-22)

Purpose: sharpen the Stage 1 findings into named threats so that candidates are judged by which threats they close, not by feature lists. Every threat cites the Stage 1 evidence that makes it real today (OSC rows from `stage1/capability-matrix.md`, DR and I rows from `stage1/dao-requirements.md`, os-map sections) or the Stage 3 dossier finding that exposed it, and the requirement IDs from `stage1/gaps.md` that would address it. Evidence types are those of the cited rows (static inspection; nothing executed).

Status: v0.2 answers the threat-model objections of the Stage 3 adversarial reviews (`reviews/security-engineer.md` TM-1..TM-10, cited below as S-TM-n; `reviews/dao-skeptic.md` TM-1..TM-10, cited as D-TM-n). All twenty were accepted; the change log in section 6 maps each to its change. v0.1 is kept unchanged at `ledger/threat-model-draft-v0.1.md`, because the reviews cite its line numbers. v0.2.2 adds T25 and asset A12 after the article was written and verified (session `session-2026-10-22-perplexity-privacy-gate.md`; dossier `dossiers/perplexity-pii-tracer.md`); nothing else in v0.2.1 changed.

## 2. Adversaries and their reach

| Adversary | Reach today | Notes |
|---|---|---|
| V1 Malicious or compromised web page | can inject instructions into any page the agent reads; can make no-cors requests to `http://127.0.0.1:<bridge-port>/api/...` (OSC-05); can bait the planner into clicking links whose text carries commit words (OSC-19) | the most likely attacker; zero cost |
| V2 Other local process (same user) | reaches the open proxy prefixes on loopback without a token (OSC-05); on Windows can read the config file since 0600 is meaningless (OSC-06); can read chrome.storage.local via Chrome's profile directory; can read any OS keystore item of the same user (aegis dossier section 8, `CredRead`) | includes any malware the user already has |
| V3 Delegated agent child (Hermes, OpenCode, DSH, or a wrapped runtime such as Goose) | runs with provider keys in its environment, full PATH, no confinement outside macOS (OSC-16, OSC-32, OSC-34); can write to the user state root through the bridge with the capability it was given, which is the whole capability (OSC-45) | a prompt-injected or buggy agent is this adversary without any intent |
| V4 Malicious or compromised add-on | content-script add-ons share the extension's full privileges (OSC-30); manifests unverifiable (OSC-31); install UI deferred so sideload is the path (OSC-61) | supply chain; today small because the ecosystem is small |
| V5 LAN attacker | bearer-over-plain-HTTP when the bridge binds a non-loopback address; a dev LAN address ships in presets (OSC-14, os-map 5.3) | only when the user opts into LAN bind, but the preset lowers the bar |
| V6 DAO insider: custodian, reviewer, sponsor, log or status-list operator | custodians set salience templates and weight functions during bootstrap (I-17); reviewers in a small pool can be captured (DR-24); a sponsor can register unbounded AI members (DR-13); single-key upgrade and mint authorities on devnet (DR-48); an operator of a log or status list can omit or split (D-TM-3, D-TM-4) | structural; the spec grants the power and names no check |
| V7 Sybil or farming participant | base membership weight per wallet (DR-10); activity rewards survive in the text (I-1); accusation and verification markets (DR-29) | economic attacker; the spec acknowledges some and bounds none |
| V8 The project itself (honest mistakes) | STATUS and capability matrix stale by ~190 commits; "implemented" claims that do not hold (OSC-24); website claims not in code (OSC-48..50, OSC-51) | not malice; a reader who trusts the documents acts on wrong premises |
| V9 Infrastructure the verifier trusts (new, S-TM-9) | RPC providers, witnesses, status-list hosts and indexers that a member's client or the DAO verifier reads from (rewards and tessera dossiers) | can lie to a display or serve a split view without breaking any signature |
| V10 Third-party authority holder (new, D-TM-1) | the upgrade authority of a shared program Resonant would build on, for example the rewards program's 3-of-5 Squads vault with time_lock 0 and a staged buffer (rewards dossier section 8; DAO skeptic RPC read) | inherited authority that Resonant's own governance cannot check |

## 3. Threats, evidence and the requirements that close them

Format: Tn: threat. Evidence. Closes with: requirement IDs. Severity is the lead's judgement (high = irreversible harm or boundary collapse; medium = contained harm or precondition for high; low = hygiene). "Necessary, not sufficient" marks a requirement that cannot close the threat alone.

### Runtime (ResonantOS)

- T1 (high) Prompt injection drives an irreversible browser action. V1 via A4 and A5. Evidence: ask and trusted modes behave identically; blocked does not stop navigation; human-only detection is regex on English text; a public-submit regression was recorded as "passed with gates" (OSC-13, OSC-19, OSC-20); the planner is never exercised by any test (OSC-18). Closes with: R19 (host-enforced gate and ceremonies), R11 (approval ledger the route requires), R10 with indeterminate outcomes routed to the human and never retried automatically (S-TM-10: the R10 engines are at-least-once and cannot make a page action idempotent; an automatic retry after an injected "failed" report worsens T1).
- T2 (high) Provider key exfiltration by a delegated child or by anything that can read a child's environment, directly or by reflection. V3 via A1. Evidence: OSC-16, OSC-33, OSC-36; PATH and full process.env passed (OSC-34); a broker that substitutes the key into request bodies toward an upstream that echoes returns it to the child (sandbox-runtime dossier, security review S-anthropics-sandbox-runtime-1, X-8). Closes with: R03 (broker, header-only injection or response scrubbing), R02 (containment), R01 (per-principal grants so a child never needs the bridge's keys).
- T3 (high) Local-process or web-page access to the bridge through open proxy prefixes; token theft from disk or chrome.storage. V1, V2 via A2. Evidence: OSC-05, OSC-04 (Origin not an authorization input; empty allowlist), OSC-06. Closes with: R05 (loopback model), R20 (channel choice), R01 (short-lived, bound grants so theft has a short life). The R03 broker channel must not be the bridge's main listener (S-TM-6; section 4, Containment).
- T4 (high) Confused deputy: a token holder has the whole capability, requests carry no principal, so any component that reaches the bridge acts as the user; and authority already exercised over long-lived connections (SSE streams, proxied connections, running add-ons, cached status lists) survives revocation (S-TM-8; `bridge-server.mjs:391, 401`; security review X-7). V3, V4 via A2 and A3. Evidence: OSC-02, OSC-45, OSC-46; one `archive-write` covers raw intake and trusted-wiki promotion (os-map 13). Closes with: R01 (with a registry of open connections keyed by grant), R21 (add-on isolation), R14 (separate promotion contract with its own gate).
- T5 (high) Silent corruption of the knowledge boundary: AI derivations promoted into human knowledge without a working human gate, or source text mixed with AI output. V3, V8 via A3. Evidence: promotion path cannot execute and the approval gate is a no-op (OSC-24); domain separation is metadata only (OSC-25); provenance directory empty (OSC-26). Closes with: R14, R11, R12.
- T6 (medium) Supply-chain substitution of an add-on, of the bridge itself, or of a dependency a candidate brings (prebuilt `srt-win.exe`, Convira `.node`, rocksdb-native and sodium-native prebuilds, cbor-extract, caret ranges in library manifests, single-maintainer packages; S-TM-4); rollback restores revoked code. V4 via A6. Evidence: OSC-31, OSC-30 (grantedCapabilities never consulted), OSC-42, ADR-038 requirement that rollback must not restore revoked authority. Closes with: R18, R04, R21, and pinned dependencies with provenance.
- T7 (medium) Crash during an uncertain side effect duplicates or loses an irreversible action; jobs flip to paused on panel load; cancel does not kill. V3, V8 via A4. Evidence: OSC-21, OSC-22, OSC-33, OSC-42. Closes with: R10, R04.
- T8 (medium) Data loss or lock-out from a torn write: every memory route throws on a corrupted JSON file. V8 via A3. Evidence: OSC-28 (bare JSON.parse, no fsync, no crash tests). Closes with: R13, R15.
- T9 (medium) Plaintext secrets and chats at rest; keys lost on restart drive users to insecure persistence. V2 via A1, A3. Evidence: OSC-10, OSC-16, ADR-022 vault deferred. Closes with: R15 against offline disk theft and other OS accounts; R02, or a separate OS account for the broker, against same-user processes, since an OS keystore item is readable by any process of the same user (S-TM-7).
- T10 (medium) Honest failover hides vendor substitution: an unresolvable model falls through to a different vendor with that vendor's key, and provider error bodies are relayed unredacted. V8 via A1. Evidence: OSC-14, OSC-17, os-map 5.3. Closes with: R08.
- T11 (low) Interoperability claims (MCP, A2A, SKILL.md, signed add-ons, "comes back whole") that the code does not implement lead integrators to wrong assumptions. V8. Evidence: OSC-48..51, OSC-31. Closes with: R06, R07, R09, R04 and, above all, accurate status documents (article recommendation, not a component).
- T21 (high, new, S-TM-1) Security-state tamper: a delegated child or add-on edits or rolls back revocation, approval, trust or key material (A10) stored where it can write. V3, V4 via A10. Evidence: security review X-1, ten dossiers (biscuit, openworkflow, hypercore, durabletask, datalad x2, identity-common-ts, tuf-js, hypercerts-lexicon, goose); OSC-45 (child writes the state root through the bridge), OSC-32 (unconfined outside macOS). Closes with: R15 (one bridge-only store no child, add-on or `archive-write` route can reach, integrity-protected under a key only the bridge holds), R02 (containment), R11 (external anchor so rollback is detected).
- T22 (high, new, S-TM-2) Approval spoofing: the agent principal mints, replays or misrepresents the approval that a human-only route requires, or frames what the human is shown (what you see is not what you sign). V1, V3 via A5. Evidence: security review X-4: every approval design in the dossiers (durabletask approval waits, openworkflow indeterminate steps, hypercore and datalad signed approvals, Goose `request_permission`, nanobrowser gate) ends in a route or prompt reachable or renderable from the extension context the planner runs in; Goose's ACP lets any client answer approvals. Closes with: R19 (ceremony rendered by a component with no agent code, constructing the signed object from the canonical action), R11 (record bound to the canonical action), R01 (the agent principal never holds the approval route's grant).
- T25 (medium, new, 2026-10-22) User content sent to a cloud provider with no content-derived sensitivity check: routing between local and cloud providers is decided only by caller-declared locality and latency/cost preference, never by anything about the message being sent, so page context or chat content that is itself sensitive can be routed to the cloud with no warning. V8 via A1, A3 (honest-mistake and no-check exposure, not an active adversary). Evidence: ADR-005 lists only "preferred runtime locality" and "latency/cost sensitivity" as routing inputs (`docs/architecture/ADR-005-provider-fabric-routing.md:105,118-119`); `allowsLocalProviderEndpoint` decides local-endpoint allowance from profile id, type and template only (`provider-bridge-service.mjs:204-245`); the only outbound content transformation anywhere is a five-pattern regex over CLI error text for keys and tokens (`addon-delegation-service.mjs:124-130`), which never runs on page context or chat content. Closes with: no existing requirement (closest is R08, which governs how a chosen destination is reached, not whether content should influence the choice); partially addressed by adding a content-derived sensitivity input to ADR-005's routing policy and to the X-4 approval helper's prompt (dossiers/perplexity-pii-tracer.md). Necessary, not sufficient: a classifier is a privacy control, not a security boundary, and does not replace R03's broker or its echo redactor.

### Governance and economy (ResonantDAO)

- T12 (high) Governance capture during bootstrap, including authority Resonant inherits. Custodians define weight functions and salience templates, hold single-key upgrade and mint authority, and the custodian transition has no trigger; a shared program under a third party's authority (V10) and the off-chain trust roots (A11) are authorities too (D-TM-1). V6, V10 via A7, A8, A11. Evidence: I-17, DR-46, DR-47, DR-48; rewards dossier section 8 (3-of-5 Squads vault, time_lock 0, staged buffer). Closes with: R24 (multisig-timelocked authorities, staged transition, listing every key class: program upgrade, mint, status-list signer, TUF root and targets, log and witness, provenance; and, from v0.2.1, the electorate-defining authorities (realm authority, voting-mint revoke and mint, voter-weight plugin configuration, quorum denominator) and the meta-authorities (custodian set, authority-spec signer), which are the cheapest capture routes because they change who votes or how much, not what executes; R24 dossier and reviews/dao-skeptic-r24.md TM-R24-1), R30 (off-chain Phase 1 keeps the blast radius small).
- T13 (high) Human-only governance undermined by self-declared human/AI splits and uncapped sponsored AI members; an AI child can sign provenance as the host when the provenance key is readable by it (D-TM-6, D-identity-common-ts-2). V3, V6, V7 via A8. Evidence: DR-13, DR-17, I-17; whitepaper "human governance rights should remain human-controlled"; nothing in the Alpha produces a human/AI split (DAO review C-6). For any binding on-chain vote (Phase 2), built-in vote delegation (spl-governance's delegate can re-delegate and the vote record keeps no trace of the signer) lets an agent-held key vote as a human (TM-R24-3). Closes with: R03 and R15 (key custody away from agents), R11 (human ceremony), R25 plus a weight plugin or off-chain rule that zeroes non-owner signers; R12 is necessary, not sufficient (a format cannot close T13; identity-common-ts dossier says so itself). Open by construction until an OS-side measurement and a human ceremony exist.
- T14 (high) Member personal data exposure, including permanent stigma: revocation and appeal records on a public chain stay linked to the wallet (D-TM-9, D-solana-foundation-rewards-6). V1 (anyone) via A9, A7. Evidence: OI-1 (community.db committed), DR-09 (membership privacy absent from the spec), "the software logs every member action" (I-14). Closes with: R23 (privacy-by-default registry with inclusion proofs), R30; no revocation reason on-chain. OI-1 is a maintainer matter held for the article (D1.3).
- T15 (medium) Credential loss, theft or wrongful revocation with no recovery or appeal: a lost key is a lost membership; a stolen non-transferable credential cannot be frozen; issuer-served revocation state can be split between verifiers (D-TM-4); a wallet can be led to sign a cross-protocol message that a verifier accepts (S-TM-9). V7, V6, V9 via A7. Evidence: DR-06, DR-07, DR-08; hub minter never freezes (DR-01); SD-JWT status list has one signer and no history (DAO review C-4). Closes with: R22, R23, with revocation state logged and witnessed in the R30 log and wallet messages domain-separated.
- T16 (medium) Collusion rings, reviewer capture, reviewer identity spoofing (an evaluator named but not signing, cheaper than capture; D-TM-5, D-hypercerts-lexicon-1), appeal flooding, verification spam, accusation markets. V6, V7 via A8. Evidence: DR-24..29, dao-requirements section 7 attack list. Closes with: R26, R27, R28; reviewer = signer.
- T17 (medium) Economic contradiction exploited: activity rewards in the text versus outcome-only in the mechanism; three contribution ladders. V7 via A8. Evidence: I-1, I-4, DR-40. Closes with: R26 (one ledger with explanation records) and a specification fix whose owner is the ResonantDAO maintainers (D-TM-10; carried to the article's communications section with OI-4).
- T18 (medium) On-chain premature commitment: minting tokens or binding votes before the evidence path works freezes design errors into deployed state (the devnet already holds a superseded model). V8 via A7, A8. Evidence: DR-36, I-5, I-6, dao-requirements section 5. Closes with: R30, R23 (anchor commitments, not balances).
- T23 (high, new, D-TM-2) Issuer-mediated transfer and recovery abuse: membership is sold or stolen through a re-binding ceremony, or a program-level operation moves a "non-transferable" credential (rewards branch `TransferPoints` burns and re-mints with holder plus issuer; D-solana-foundation-rewards-1, -5). V6, V7 via A7. Closes with: R22, R25; re-binding cannot be used to transfer, demonstrated by a fault test.
- T24 (medium, new, D-TM-3 and DAO review C-5) Operator omission and split view: a log, ledger, status-list or registry operator drops claims, appeals or contests, serves different state to different readers, or inflates membership behind commitment-only entries; edits are made while no indexer watches. V6, V9 via A8, A7. Evidence: D-transparency-dev-tessera-2, -3; D-identity-common-ts-4; D-hypercerts-lexicon-2. Closes with: R30 (witnessed log with signed submission receipts and auditable entry-type counts), R26, R23.

### Cross-boundary (OS and DAO together)

- T19 (high) DAO state grants or removes runtime capability without a per-item user act: a DAO credential, role or vote becomes runtime authority; a certification revocation disables installed add-ons remotely (kill switch or censorship; D-TM-7, D-tuf-js-1); or OS data flows to the DAO without a per-item user act. V6 via A2, A3, A6. Evidence: no code yet; the spec text "logs every member action" (I-14) versus interaction invariants I2 and I3; tuf-js dossier design (removal from `certified` auto-disables). Closes with: the invariants themselves (constraints on every candidate in branches F and G), R12 (claim packages with selective disclosure), R11 (local consent log), R18 with user confirmation before a remote disable takes effect.
- T20 (medium) Attribution collapse: human/AI portions are not carried from harness session into any record, so the DAO cannot apply its own attribution rule. V7 via A8. Evidence: interaction section 12 (E3 downgraded to C), OSC-35; DAO review C-6. Closes with: R12, R07 (both necessary, not sufficient; see T13).

## 4. Properties a candidate must demonstrate (per threat family)

These are the scoring properties (`scoring/weights.json`, isolation_and_security anchor as clarified in D3.7); a candidate that only claims a property scores as B at best. Each property check names the full condition under which the primitive yields the property and an acceptance fault that breaks it (DAO review C-3).

| Family | Must demonstrate (with test, audit or reproducible example) |
|---|---|
| Authorization (T3, T4) | a revoked or attenuated grant is refused mid-session, including on open streams and running units; grants carry principal identity; verification works offline |
| Containment (T2, T3) | filesystem, network and exec escapes blocked on each OS, or an honest "unconfined" signal; child cannot reach the loopback port unless granted; the broker channel is not the bridge's main listener and is the only bridge surface a confined child can reach (S-TM-6) |
| Secrets (T2, T9) | child never sees the key, including through upstream echo, error bodies or reflection (echoing-upstream fault test); per-call audit; works for OpenAI-compatible HTTP (S-TM-5) |
| Security state (T21) | security state unreachable by children and add-ons (fault: a child with `archive-write` tries to edit each file); rollback of it detected |
| Approval and audit (T1, T5, T19, T22) | route refuses without an approval record; the approval record cannot be created by the agent principal; the human is shown the canonical action the record binds (fault: agent asks for A while displaying B); user-readable export. Tamper evidence split (S-TM-3): (a) against non-same-user corruption, a local hash chain suffices; (b) against a same-user attacker (V2, V3), only an external checkpoint or a separate OS account; each R11 design states which it meets, and Phase 1 needs (b) for anything that gates T1 or T22 |
| Component surface (T3, T6; new, S-TM-4) | no new listener without authentication and without exclusion from confined children; parsers of child or page input run outside the process holding A1 and A2; dependencies pinned with provenance |
| Browser gating (T1) | gate outside the DOM; adversarial injection suite with measured results; MV3-compatible |
| Durability (T7, T8) | recovery after crash during an uncertain side effect with no duplicate; indeterminate outcomes go to the human, never to automatic retry; torn-write test |
| Supply chain (T6) | signature and hash verified offline; revocation survives rollback, including rollback of the client's own cache; substitution test |
| Provenance (T5, T13, T20) | human/AI attribution and tool identity expressible and produced by a measurement the attributed agent cannot forge; selective disclosure verifiable; anchoring demonstrated |
| Credentials (T15, T23) | non-transferability tested at program level, not only by token extension; issuer revocation recorded with reason, authority, evidence and appeal deadline, reversible with history (DR-06); re-binding fault test showing it cannot be used to transfer; audit report; Solana or stated otherwise (D-TM-8) |
| Governance (T12) | multisig and timelock on every authority, including inherited ones, off-chain trust roots and every authority that sets voter weights, the electorate or the quorum denominator; insiders hold at most k-1 of any k-of-n; a veto or cancel reachable by a party other than the approving quorum, at a threshold that party can actually reach, inside the delay (TM-R24-1, TM-R24-2); voter-weight plugin; documented failures |
| Accounting (T13, T16, T17, T24) | explanation records; reviewer independence; reviewer = signer; appeal bound; signed submission receipts; auditable entry-type counts; post-mortems of farming |
| Minimal architecture (T11, T18) | thin layer keeps the A/B features; off-chain Phase 1 covers membership, claims, advisory votes with public auditability |

## 5. What this draft does not cover yet

- Denial of service against the bridge and the user's own machine (resource exhaustion by a delegated child); folded into R02 and R04 for now.
- Legal and licence threats (Augmentor relicensing, OI-3; seven org repos without a licence; git-annex AGPL-3.0-or-later found by the DataLad inspector); tracked in census-notes and the dossiers' section 9, held for the article.
- Accessibility and friction costs of the ceremonies (interaction section 9); weighed in the article, not here.
- Coverage gap (DAO review C-7): T12 closes with R24, T13 with R25 and T16 with R27, and none of these three requirements has a Stage 3 dossier. Gate 2's "not shortlisted" list names Realms and Squads v4 for R24 and HotCRP and go-eigentrust for R27. Either the article states this limit or one more inspection runs (Gate 3 decision).
- The architecture decisions that the new properties force (one bridge-only security-state store, an approval path the agent cannot drive, the broker transport relative to containment) are Gate 3 work, not threat-model text.
