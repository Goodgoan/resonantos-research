## X-1 One bridge-only security-state store

### Decision

1. **Location.** `<stateRoot>/security/`, where `stateRoot` is the per-OS directory the Alpha already computes in `defaultHarnessStateRoot()` (`harness-registry-store.mjs:6-10`): `%LOCALAPPDATA%\ResonantOS` on Windows, `~/Library/Application Support/ResonantOS` on macOS, `$XDG_STATE_HOME/resonantos` (default `~/.local/state/resonantos`) on Linux. It is never a subdirectory of `~/ResonantOS_User` and it is never part of the portable user folder (ADR-022 "copy this folder to a new computer" covers user data; security state must not travel by copy, because a copy is a rollback). The directory is created `0700` and files `0600` on POSIX by the existing writer; on Windows the first PR adds an explicit owner-only DACL, because `mode` is meaningless there (OSC-06).
2. **What goes there (the ten designs the security review listed under X-1, plus three added by this decision).**

| Owner (requirement) | Files under `security/` | Today's proposed location, now withdrawn |
|---|---|---|
| R01 Biscuit grants | `grants/revocations.jsonl` (append-only), `grants/root-key` (only if persisted; default per-run in memory) | `~/ResonantOS_User/bridge-revocations.json` |
| R18 TUF verifier | `addon-trust/watermark.json`, `addon-trust/revoked.jsonl`, last verified `root.json` copy | `<stateRoot>/addon-trust/` unprotected; harness state root |
| R11 approval ledger | `approvals/ledger.jsonl`, `approvals/HEAD.json` (pinned checkpoint), `approvals/signing-key` | `~/ResonantOS_User/Logs/audit-ledger.jsonl` |
| R10 durable jobs | `jobs/openworkflow.db`, `jobs/intent-journal.jsonl`, sidecar token (if durabletask is ever used) | `<userRoot>/BrowserFirst/Jobs/`, `~/ResonantOS_User/state/` |
| R14 git ledger | `memory-git/<domain>.git` (git directories only; work trees stay in the memory root), `memory-git/allowed_signers`, `memory-git/approval-key` | `.git` inside the memory domains; home directory |
| R12 provenance | `provenance/issuer-key`, `provenance/receipt-keys.jsonl` | `~/ResonantOS_User/CONFIG` |
| R07/R29 Goose adapter | `goose/permission.template.yaml` (bridge-held copy compared after every turn) | Goose's own config directory |
| R03 broker (X-5) | `broker/audit.jsonl` (written by the bridge from the broker's control pipe) | bridge memory only |
| R19 approval helper (X-4) | `approvals/enrolment.jsonl` (Phase 2 credentials) | not previously placed |
| Harness governance watermark (existing) | moves from `<stateRoot>/harness-governance/*.watermark.json` into `security/harness-governance/` in a later PR; unchanged in the first PR | `<stateRoot>/harness-governance/` |

3. **Reachability, three layers, each honest about what it covers.**
   - (i) **No bridge route reaches it.** `isInsidePath` and the path helpers (`browser-first-host-utils.mjs`, `archive-promotion-paths.mjs`, `memory-source-paths.mjs`) gain a deny for `stateRoot` as a whole, so none of the eight `archive-write` routes (`memory-host-service.mjs:134-212`), no intake, move or user-data route, and no add-on route can read or write it. This closes T21 for V1 (no-cors requests to the bridge) and V4 (content-script add-ons calling bridge routes), and for V3 through the bridge (OSC-45). The store is written only by `security-state-store.mjs`, which no route handler imports for arbitrary paths.
   - (ii) **No confined child reaches it.** Every delegation profile lists `stateRoot` in the read-deny set and never in a write grant: `denyRead` under sandbox-runtime, `denyPaths` under a Convira-pattern backend, `(deny file-read* file-write*)` under the macOS seatbelt profile. The existing `readDenyRootsFor` list (`delegation-isolation.mjs:175-209`) covers only `ResonantOS_User/Secrets` and macOS browser paths; this decision adds `stateRoot` to it in the first PR, independent of which containment backend lands. This closes T21 for confined V3 on Linux and macOS, and on Windows only when the opt-in srt-win install is present.
   - (iii) **Where the child is unconfined (`contract-only`), the store is same-user exposed.** The bridge records that fact in the governance audit (the existing `contract-only` operator-override path, `delegation-isolation.mjs:54-65`), and the integrity layer below gives level (a) only: a same-user process can read the MAC key from the credential store and rewrite records and head undetected (item 5). The article reports this as the Windows default today. (Corrected 2026-10-21 after the article's adversarial review, objection 7; the earlier wording "detects tamper and rollback but cannot prevent it" contradicted item 5.)
4. **Integrity protection.** Every record written under `security/` is `{v:1, revision, payload, prevMac, mac}` with `mac = HMAC-SHA256(key, canonical(v, revision, payload, prevMac))`, written through the existing atomic temp-file, fsync, rename writer (`harness-registry-store.mjs:23-70`), whose fail-closed test already exists ("a rolled-back registry file fails closed and resurrects no consent", `harness-registry.test.mjs:150-180`). Append-only files chain on `prevMac`; state files carry the chain head. One `security/HEAD.json` carries `{revision, lastMac}` across all files and is itself MAC'd.
   - **Key custody.** The MAC key is 32 random bytes held in the OS credential store (Windows Credential Manager via DPAPI, macOS Keychain, Linux Secret Service) under service `ResonantOS`, item `security-state`. Where no credential store exists (headless Linux without a keyring daemon), the key lives in `security/mac-key` `0600` and the bridge labels integrity "same-user, file-backed". The Alpha has no keyring dependency today; the first PR takes `@napi-rs/keyring` or the platform CLIs (`security`, `cmdkey` plus PowerShell `CredRead`, `secret-tool`) behind an interface, pinned, with the Aegis dossier's finding in mind: the item is readable by any process of the same user (`credential-manager-windows.ts:22-55` pattern). This gives level (a), not (b), and the decision says so.
   - **Rollback detection.** The head revision is mirrored into the credential-store item beside the key (`{key, headRevision, headMac}`). On start the bridge compares `security/HEAD.json` with the mirror: a lower revision or a different MAC means the files were restored from an older copy; the bridge then refuses to serve grants, trust verdicts and approvals (fail closed) and raises a visible alarm. An attacker who can also rewrite the credential-store item defeats this; that is the level (b) residual against V2.
   - **No Guardian baseline covers it.** ADR-038's future rollback must exclude `security/` or treat it as tighten-only state (tuf-js dossier section 7 item 5), so a known-good rollback cannot restore revoked authority (T6).
5. **Level (b) path, stated and deferred.** On one OS account, no local design detects a same-user attacker who can read the key. Two closures exist: (1) **external checkpoint**: `exportHead()` writes the signed head as a short text the user keeps elsewhere, optionally on a second device or a user-chosen witness (off by default, I1 and I3; this is the hypercore and tessera dossiers' step 5); (2) **separate OS account**: the security-state owner (the authority core of reference architecture A2) runs as a service under its own account (Windows service, macOS LaunchDaemon, systemd system unit), which is the only local closure against V2 and the one the threat model names (T9 closure). Phase 1 ships (1) as an export; (2) is an A2 milestone. Until then, routes that gate T1 or T22 rely on R02 containment for V3 and declare V2 on the same machine out of scope; the article says this in plain words.

### Rejected alternatives

- **Keep security state under `~/ResonantOS_User` with 0600.** Rejected: the user root is written by children through the bridge (OSC-45) and directly when unconfined (OSC-32); 0600 is meaningless on Windows (OSC-06). Ten dossiers proposed this; all ten amendments withdrew it.
- **Encrypt the files instead of MAC them.** Rejected as insufficient alone: encryption without a head mirror does not detect rollback, and the key custody problem is identical. Encryption at rest is an R15 concern (T9, offline theft) and can be added over the same store later.
- **A per-boot key only (no persistence).** Kept as the default for the Biscuit root key (restart invalidates grants, matching today's behaviour), but rejected for revocation sets, watermarks and ledgers, which must survive restart and rollback by definition (T6, I6).
- **Put the store in the credential store itself.** Rejected: items are size-limited and the store is same-user readable anyway; only the key and the head mirror belong there.

### Acceptance (ids in `acceptance-backlog.md`)

- X1-a (shared case the security review asked for): a child with `archive-write` tries to create, edit, truncate, delete and replace with an older copy each file class above, through every bridge route and, in `contract-only` mode, directly; expected: every route refuses; direct edits are detected at the next read (MAC failure) and a rollback is detected at start (head mismatch).
- X1-b: restore `security/` and the credential-store item together from a pre-revocation snapshot; expected: not detected, documented as the level (b) limit (tuf-js 6b analogue).
- X1-c: credential store absent; expected: file-backed key, visible "same-user, file-backed" label, no silent degradation.
- X1-d: Windows DACL check; expected: only the user's SID has access.

## X-4 An approval path the agent cannot drive

### Decision

1. **The ceremony component is a separate process spawned by the bridge, the "approval helper".** It is not the side panel, not the service worker, not any extension page, and not a bridge route. Its only input is an inherited pipe from the bridge; it opens no listener (X-6). It contains no agent code by construction: the process image is the helper alone. Why not an extension page with a strict CSP: the extension is one origin in which the planner loop runs (`ext/src/side-panel.js:783-908`, os-map section 7), content-script add-ons share its privileges (OSC-30), the service worker holds all 26 tokens (OSC-02), and WebAuthn inside MV3 pages is unverified (hypercore dossier q2); nothing inside that origin can be shown to contain no agent code.
2. **What the helper renders is the bridge's canonical action, never the agent's description of it.** The bridge sends `{approvalId, route, principal, canonicalBody, targetHost, digest, nonce, agentIntentText?}`. The helper shows route, target, the canonical body (or a bridge-generated summary plus the digest for long bodies), and the agent's intent text only under the caption "requested by the agent, its own words" (the nanobrowser card pattern, `cards.test.tsx:38-55`). It recomputes the digest of what it rendered and returns `{approvalId, renderedDigest, decision, nonce}`. The bridge accepts only if `renderedDigest` equals its own digest and the nonce matches; any mismatch is refused and logged. This is the "what you see is what you sign" rule (X-4 fault: agent asks for A while displaying B).
3. **There is no approval route.** Decisions arrive only over the helper's pipe. No capability token, Biscuit grant or extension message can produce one, so the agent principal never holds the approval route's grant because the route does not exist. The planner may *request* an approval (a 428 `APPROVAL_REQUIRED` answer carries the id, as the hypercore dossier sketches); it cannot answer it.
4. **Record before act.** On a decision, the bridge appends `{type:"approval", approvalId, route, principal, actionDigest, decision, ceremony:{helper, version, method}, ts}` to the R11 ledger in the X-1 store, consumes it on first use, and only then runs the handler; if the append fails, the route refuses (the CATP fail-closed pattern). Each approval covers one action; "always allow" is itself a separate ceremony and record, and the agent's answer never writes a persistent allow (the Goose `permission.yaml` lesson, S-aaif-goose-1).
5. **Enrolment and the human proof, by phase.**
   - Phase 1: the helper uses the operating system's native dialog from a dedicated child process (Windows: a PowerShell-hosted WinForms dialog; macOS: `osascript` display dialog; Linux: `zenity` or `kdialog`, falling back to a terminal prompt attached to the bridge's console). The proof is the decision bound to the bridge nonce. This gives the process boundary and zero agent code with no new dependency. Its limits are stated: text rendering only (diffs are shown as a summary plus digest, with the full diff written to the X-1 store for the user to open), and no resistance to synthetic input from a same-user process.
   - Phase 2: a small signed helper application adds user verification (Windows Hello `UserConsentVerifier`, macOS LocalAuthentication, polkit on Linux, or a WebAuthn authenticator with user verification), enrolled in a first-run out-of-band ceremony through the helper; later credentials require an assertion from an existing one; every enrolment and removal is an R11 record; virtual authenticators are refused where attestation allows (S-holepunchto-hypercore-2). Per-OS availability of these primitives is a hypothesis until acceptance X4-d runs.
6. **Which routes are gated in Phase 1.** Archive promotion (the `archive-write` capability is split: a new `archive-promote` capability covers promote and restore, as os-map seam 3 asks), delegation start with execution enabled (closing the per-request opt-in bypass, OSC-33), provider credential writes, add-on grant changes, TUF revocation overrides (D4.0 (3)(a)), and the indeterminate-step decision of R10 (openworkflow dossier step 5). Public submit, pay and grant classes in the browser execute in the content script today (OSC-20) and are covered only once the extension requests a bridge-issued execution ticket for them (R19 port, nanobrowser dossier G5 conditions); until then the worker-side gate is the last line and the article says so.
7. **Fallbacks.** No helper available (headless, CI, a helper crash): gated routes refuse with `NEEDS_USER`; the bridge never falls back to a UI approval, to `actorType:"human"` strings (`archive-review-policy.mjs:18-36`), or to automatic retry of an indeterminate step (T1 closure).
8. **Attacker model.** Closes T22 against V1 (a page cannot reach the helper), V4 (an add-on cannot answer, there is no route), confined V3 (no pipe, no listener), and the prompt-injected planner (it can request, not render or answer). Not closed against V2 or an unconfined V3 that synthesises clicks or keystrokes on the helper window; Phase 2 user verification narrows that, and only R02 containment or a separate session closes it.

### Rejected alternatives

- **A separate extension page with no agent code and a strict CSP** (hypercore dossier option 2). Rejected for Phase 1 because the extension origin cannot demonstrate the absence of agent code (OSC-30) and because WebAuthn availability in MV3 pages is unverified. Kept as a Phase 2 experiment only if the helper process proves unworkable on some OS.
- **A bridge route guarded by a second token the extension does not hold.** Rejected: the token would live in the same extension or on the same disk the agent reaches; the review's point is that no route reachable from the agent's context should exist.
- **Nanobrowser-style service-worker card.** Rejected as the approval of record: the worker is the agent's own context in the Alpha, and nanobrowser's own README concedes that anything with extension privilege can answer a card. Its classifier and card layout are still ported for the browser gate (R19).
- **WebAuthn gesture as the whole proof** (the original hypercore design). Rejected on its own: it proves a touch, not consent to a rendered action (S-holepunchto-hypercore-1). It returns in Phase 2 as user verification *inside* the helper that renders the canonical action.

### Acceptance

- X4-a (shared fault): the injected planner requests approval for action A while the side panel displays action B; expected: the helper shows A from the bridge's canonical body, a decision given for B does not verify for A (digest mismatch), no handler runs.
- X4-b: the agent principal, holding every capability token, tries every route and extension message to produce an approval; expected: none exists; the only observable is a 428 with an id.
- X4-c: helper absent or killed mid-ceremony; expected: `NEEDS_USER`, no side effect, no retry.
- X4-d (Phase 2): enrolment from the agent principal refused; virtual authenticator refused or flagged; per-OS availability of user verification measured.
- X4-e: append failure of the R11 ledger (read-only store); expected: route refuses.

## X-5 The R03 broker and its transport

### Decision

1. **Implementation: an Aegis-pattern reverse broker, reimplemented in Node, in its own process.** Not sandbox-runtime's `srt proxy`, not Aegis as shipped. The broker holds provider keys only (delivered over stdin at spawn, never by environment, S-dapr-durabletask-go-3), never bridge tokens, and exposes exactly one service: credential injection for one virtual provider host. The bridge talks to it over an inherited pipe for control (issue grant, revoke grant, audit row, key rotation). The bridge's main listener carries no broker route and the broker listener carries no bridge route (`bridge-route-capability-audit.test.mjs` gains an assertion that no `/broker` prefix exists on the main table, as the aegis dossier proposes).
2. **How a child reaches it: as the containment layer's external HTTP proxy, with one virtual host.** The broker listens as an HTTP forward proxy on a dedicated loopback port (`127.0.0.1:<random>`, never `0.0.0.0`, the Aegis defect) and is handed to the containment layer as the external proxy:
   - Linux (sandbox-runtime): `network.httpProxyPort = <broker port>`; srt then skips its own proxies and relays its Unix socket into the child's network namespace, where a socat listener on port 3128 is what `HTTP_PROXY` points to (`linux-sandbox-utils.ts:1514-1528, 3729`). The host loopback, and so the bridge port and its open proxy prefixes (OSC-05), stays unreachable because the child has its own namespace.
   - macOS (sandbox-runtime): the Seatbelt profile allows outbound only to `localhost:<broker port>` (`macos-sandbox-utils.ts:1317-1343`); the bridge port is not in the profile. `allowLocalBinding` is never set.
   - Windows with the opt-in srt-win install: the broker port sits inside the WFP-permitted loopback range for the `srt-sandbox` account; the anonymous-token residual means a child written to defeat the fence reaches other loopback ports too, so the label stays "bypassable" (D3.10).
   - Unconfined (`contract-only`, the Windows default today): `HTTP_PROXY` and the base URL are plain environment variables; the broker's per-delegation token is the only barrier, the same class of weakness as today's bridge tokens (T3); the governance audit records "unconfined: broker reachable by any local process holding the token". The key is still never in the child's environment, which is an improvement on OSC-16 even unconfined.
   - The child's environment: `HTTP_PROXY`/`HTTPS_PROXY` (set by the containment layer or, unconfined, by the bridge), `OPENAI_BASE_URL=http://broker.resonantos.invalid/v1` (an `.invalid` name, so it resolves nowhere outside the broker), `OPENAI_API_KEY=<per-delegation token>`, and for Hermes the existing `RESONANTOS_HERMES_BASE_URL` and `RESONANTOS_HERMES_API_KEY` (`addon-delegation-service.mjs:1649-1659, 1770-1782`). No provider key, no `PATH` of the host (OSC-34), no `process.env` spill.
3. **What the broker does per request (the Aegis order, with the review's fixes).** Token (SHA-256 lookup of the delegation token) and grant (not revoked, not expired, principal recorded); the virtual host `broker.resonantos.invalid` is the only host with credential injection; any other absolute-URI or `CONNECT` target is checked against the bridge-chosen domain allowlist for that delegation (default deny; the external proxy "must handle domain filtering", `sandbox-config.ts:760-777`) and, if allowed, relayed without any key; strip `authorization`, `x-api-key`, `proxy-authorization`, `cookie`, `host`, any `x-target-host` (the route is bridge-chosen, never child-supplied); inject the real key **header-only** (never body, never query; providers that take `?key=` are routed through a bridge-side adapter, srt issue #752 pattern); forward with the bridge's existing `fetchProviderResponse` logic over HTTPS to the real provider; relay the response through a **redactor** that replaces the exact key and its base64 and URL-encoded forms in every header and body chunk, with a carry-over of key length minus one bytes across SSE chunks (the echoing-upstream property, TM-5, X-8); fixed bodies for the broker's own 4xx and 5xx (no provider error body relayed verbatim, fixing the T10 note for this path); refuse `TRACE` and `TRACK`; write an audit row `{delegationId, principal, host, method, status, bytes, ts}` over the control pipe, which the bridge appends to `security/broker/audit.jsonl` (X-1).
4. **Revocation mid-session (X-7).** A `Set<AbortController>` per grant; `revokeGrant(delegationId)` on delegation end, cancel, execution-settings off, bridge shutdown and key rotation aborts every open upstream request and closes the client connection within one chunk; client disconnect aborts the upstream request too (the property Aegis lacks). Grants expire by default at the delegation's own deadline.
5. **sandbox-runtime's role is containment only.** The isolation adapter rejects any `credentials.envVars` mask entry (S-1, S-4), never enables `tlsTerminate`, passes `httpProxyPort` and `socksProxyPort` (the broker also answers SOCKS CONNECT with the same allowlist, or the SOCKS port is pointed at a deny-all stub), and validates its config with `SandboxRuntimeConfigSchema.parse()` before `initialize()`. The srt proxies therefore never run in the bridge process (S-2), and no MITM CA is installed in any child.
6. **Process placement.** Phase 1 (reference architecture A1): the broker is a child of the bridge, same OS user, keys passed on stdin at spawn from the bridge's in-memory credential map (`provider-bridge-service.mjs:49-54`). Phase 2 (A2): the broker becomes the only process holding provider keys, started by the authority core, with the bridge itself calling providers through it; a separate OS account for the broker is the level (b) closure against V2 (T9 closure wording).

### Why this beats the two alternatives

| Criterion | Aegis-pattern reverse broker (chosen) | `srt proxy` forward proxy with decider | Aegis as shipped |
|---|---|---|---|
| Key reaches the child by echo | No: header-only injection plus a response redactor | Header-only by design, but responses are relayed unscrubbed (`proxy-only.ts`, dossier section 5 point 5); a Resonant relay would be needed anyway | No redaction (`gate.ts:1380-1381`, authors' residual I-2) |
| Needs a MITM CA in the child | No: the child speaks plain HTTP to a virtual host; the broker does HTTPS upstream | Yes for HTTPS targets (TLS termination; Hermes needs `SSL_CERT_FILE`); the Windows CA key sits in `%ProgramData%` (S-5) | No |
| SDK change in the child | Base URL and key only, which the Alpha already parameterises (`RESONANTOS_HERMES_BASE_URL`) | Proxy env only, but then every allowed host, not one virtual host, is a credential target unless `injectHosts` is right | Custom `X-Aegis-Agent` header that stock OpenAI clients do not send; port-443-only upstream; body inspection refuses chat payloads |
| Listener surface | One loopback port, one route, token-checked, no stats, no dashboard | Unauthenticated on TCP (`--listen` row); Unix socket needs `--listen-fd` and the relay question (open q 11) | Binds all interfaces, unauthenticated stats and dashboard (D3.11) |
| Maturity of the exact code path | Our code, about 400 lines, unscored (clause (c)); tests A, A2, B, E from the aegis dossier become ours | Two weeks old at inspection (`c6d5baa`, 2026-10-07) | Single maintainer, idle 75 days |
| Per-OS transport | Uniform: the containment layer's external-proxy plumbing on all three OSes | Same plumbing; same residuals | Loopback TCP, which AppContainer cannot be granted |

The chosen design reuses exactly the piece of sandbox-runtime that is tested on all three OSes (the proxy plumbing into the sandbox) and discards the piece the review refuted (body substitution with unscrubbed responses).

### Rejected or deferred

- **Convira AppContainer on Windows as the Phase 1 broker transport.** Deferred to Phase 2. AppContainer can never be granted loopback (convira dossier section 7, conflict 1), and a network-enabled AppContainer child gets Internet plus LAN with no proxy, so under Convira a child either cannot reach any provider or holds the key itself. A named pipe with a per-SID DACL is possible in principle (the SID is derivable before launch) but no child runtime in the Alpha speaks a named pipe. Convira stays the no-admin Windows option for tasks that need no network, and the first PR for its vendored backend (full native review, A10) proceeds independently of R03.
- **A Unix socket bind-mounted into the child as the only transport.** Rejected for SDK reasons: Hermes (Python httpx) and OpenCode (Node) take a base URL, not a Unix socket; the relay into the namespace gives them a loopback TCP endpoint for free and keeps the host loopback out of reach.
- **Broker in the bridge process.** Rejected (S-2, X-6): the parser of child-controlled bytes must not share a process with A1 and A2.
- **DSH and `opencode serve` servers that the bridge connects to** cannot run inside a Linux network namespace (sandbox-runtime dossier break point). They stay on the CLI path or unconfined until a reverse channel exists; not an X-5 matter, recorded in the risk register (RR-12).

### Acceptance

- X5-a (X-8 shared case, ranked test 2 and 5 in `acceptance-backlog.md`): an echoing provider stub returns request headers and body in 200 and 4xx bodies and in SSE split across chunks; the child posts the token in `model`, in a message, in `X-Echo`, URL-encoded and base64; expected: the child's output never contains the real key in any encoding.
- X5-b (confinement): on each OS the confined child connects to the bridge port, to 1.1.1.1:80 and to an unlisted host via the proxy; expected: refused; only the virtual host succeeds.
- X5-c (X-7): revoke during a streaming completion; expected: the stream ends within one chunk; the next request is 403.
- X5-d: the broker's listener is `127.0.0.1` only and carries exactly one route; `CONNECT` to a non-allowlisted host is refused; `TRACE` refused.
- X5-e: unconfined Windows: the token-only barrier is recorded, not hidden; a second local process with the token can spend the key (documents the residual).

## Cross-cutting rules that follow from the three decisions

1. **Component surface.** Every new process (broker, approval helper, isolation broker) opens either no listener or one authenticated loopback listener that confined children cannot reach, and parsers of child or page input never run in the process that holds A1 and A2. The bridge process keeps the bridge tokens and, in Phase 1, provider keys in memory until the broker spawns; in Phase 2 only the broker holds provider keys.
2. **One revocation vocabulary.** Grants (R01), delegation tokens (R03), add-on trust (R18), credentials (R23) and approvals (R11) all revoke through records in the X-1 store with a stated bound: next request plus open-stream abort for grants and tokens; hourly recheck or push for add-ons; one verification for credentials. Every revocation record carries its reason class (security or policy, D4.0 (3)(a)).
3. **Honest degradation.** `contract-only` on Windows is reported as unconfined in the governance audit, the security store as same-user exposed, and the broker as token-only; nothing silently no-ops (G2).
4. **Scoring.** None of the three designs receives a numeric score (D4.0 (3)(c)); each reference architecture in `reference-architectures.md` carries an acceptance checklist against the threat-model properties, all rows "designed, not yet tested".
